# 地図の表示範囲とカメラ移動の設計

「どこを映すか」「ピンを選んだときどう動かすか」の規則。計算は
`packages/shared/src/placeMap.ts` の純粋関数に集約し、web（`place-map.tsx`）と
iOS（`(tabs)/places.tsx`）が同じ規則で動く。

## 1. 初期表示は「ピンが集まっているところ」だけを映す

**全ピンの外接矩形は使わない。** 旅行のピンは大抵ひとつのエリアに集まるが、
帰りの空港のように遠く離れた点が1つ混ざる。それを含めて範囲を取ると、誰も居ない
海の上が中心の、極端に引いた画になる。

```
場所（座標あり）
  → clusterPlaces()     エリアに分ける（隣接ピンの間隔 < CLUSTER_GAP_KM=100km で連結）
  → dominantCluster()   最多ピンが単独で最大ならそのクラスタ。同数で割れていたら null
  → 主役があればその点群、無ければ全ピン に対して boundsOf() / centerOf()
```

**主役が決まらないとき（例: 1点ずつ2エリア）だけ全体に合わせる。** どちらを
見せるべきか機械的に決められないため。

実例: ハワイ旅行に成田のピンが1つある場合、主役はハワイのクラスタ。成田は初期
表示の計算から外れる（ピン自体は地図に出るし、一覧にも残る）。

## 2. 経度は日付変更線を跨ぐ。中心を自前で計算しない

`boundsOf()` は**全点を囲む最小の弧**を返す。太平洋を挟む2点（成田 ≈ +140、
ホノルル ≈ −157）で素朴な min/max を取ると逆回り（298°）を囲んでしまうため、
経度を円環とみなして最大の空きギャップを除いた残りを bounds にしている。
**跨ぐ方が短ければ `west > east` を返す**（Google Maps はこれを跨ぎと解釈する）。

そのため:

- **中心は必ず `centerOf(bounds)` を使う。** `(west + east) / 2` を自前で書かない。
  跨ぎの bounds でそれをやると地球の反対側が中心になる（成田＋ホノルルで
  **モロッコ**が出た実バグ）。
- **経度スパンも跨ぎを考慮する。** `east - west` は跨ぎで負になる。
  `west <= east ? east - west : east + 360 - west`。

## 3. ピン選択時のカメラ移動

本家 Google マップと同じく **ズームは変えずパンだけ**。既にほぼ狙い位置にある
ピンは動かさない（各軸10%以内なら据え置き）。

| | 狙い位置 | 現在の表示範囲の取り方 |
|---|---|---|
| web | 画面中央 | `map.getBounds()` / `map.getCenter()` |
| iOS | 画面の上から約25% | `map.getMapBoundaries()` |

**iOS だけ上寄せなのは、下から出るフォームシートにピンが隠れるため**（web は
タップ位置のポップオーバーなので中央でよい）。

**表示範囲は必ず地図から直接取る。React の state を基準にしない。** state は
スナップショットで、ジェスチャ中や直前のカメラアニメーションが収まっていない間は
古い＝広い値を掴む。iOS はオフセットが表示範囲の高さに比例するので、古い広い値を
掴むとオフセットが桁違いになり地図が全く違う場所へ飛ぶ（実バグ）。

iOS はピンタップ時に Google SDK 既定の「ピンを中央へ」アニメーションが走るので、
**動かさない判定のときも現在中心への移動を発行して打ち消す**必要がある。

## 4. 検索の基準位置 —— 地図は「見ている範囲」、それ以外は「旅程」

場所の検索は Google に地理バイアスを渡す。**その基準は検索する場所によって違う。**

| どこの検索 | 基準 | 実装 |
|---|---|---|
| 地図の検索窓（場所タブ） | **今見えている範囲**（矩形） | `biasRect` |
| 予定・費用フォームの場所欄 | 旅程から引いた「その時どこにいたか」、無ければピンの重心 | `biasCenter`（`tripBiasCenter`） |

分かれるのは、**利用者が既に答えを示しているかどうか**が違うから。地図では画面
そのものが「ここを探したい」という意思表示になっているが、フォームには地図が無く、
何も言っていないので旅程から推すしかない。

両方を同じ基準（ピンの重心）にしていた頃は、片方が必ず壊れた。実例: サンフランシスコ
にピンが集中している旅行で、ロサンゼルスを映して検索してもサンフランシスコの店が
返ってきた。重心は「旅行全体でどこに行ったか」の答えであって、「今どこを探しているか」
の答えではない。

**中心＋半径ではなく矩形を渡す。** 半径にすると画面との対応が崩れ、どれくらいに
するかの匙加減が要る（広すぎれば隣の街が混ざり、狭すぎれば画面の端が外れる）。
矩形なら画面に写っている範囲とバイアスが一致する。Places API も Maps JS も矩形を
受け取れる。

**日付変更線を跨ぐ範囲は west > east のまま渡す。** Places API の Viewport は
「low.longitude > high.longitude なら跨いでいる」と定めているので、正規化すると
地球の反対側を指す（2節と同じ落とし穴）。

範囲は 3 節と同じ理由で**地図から直接取る**（web は `idle` で `map.getBounds()`、
iOS は検索の直前に `map.getMapBoundaries()`）。地図がまだ範囲を持たない一瞬だけ
`biasCenter` に落ちる。
