# フライト番号から予定を埋める

便名（`ZG002`）を入れると、出発地・到着地・時刻・タイムゾーンが埋まる機能の設計。
実装は `packages/shared/src/flight*.ts` と両プラットフォームの `flight-picker`。

## 0. なぜこの形か（先に読む）

この機能の設計は**実際に API を叩いて測った結果**から決まっている。想像で決めると
外す点が3つあるので、根拠を残す。

| 測ったこと | 結果 | 設計への影響 |
|---|---|---|
| 未来の実データはどこまで有るか | 日系で約半年、United で8ヶ月 | **予測フォールバックが必須**。無いと主用途（数ヶ月前の予約）で使えない |
| 便名から時刻はどれだけ安定か | 15ヶ月間、出発時刻はほぼ 19:10 で不動（1日だけ 19:05）。到着は 07:05〜07:50 に散る | 予測は**出発時刻をそのまま写す**。到着は写さず計算する |
| 便は毎日飛ぶか | **飛ばない**。ZG002 は隔日運航＋運休期間あり | 予測の元は当てずっぽうに近隣日を叩かず、**運航日一覧で当たりを付ける** |

## 1. データ提供元

**AeroDataBox**（RapidAPI 経由・Basic は無料）。他社と比べた決め手は料金ではなく
**1回の応答で空港の座標と IANA タイムゾーンまで返ること**。

| | AeroDataBox | Amadeus | Aviationstack |
|---|---|---|---|
| 無料枠 | 300照会/月 | 2,000/月 | 100/月 |
| 未来 | ±365日 | 361日 | 7日以降 |
| 過去 | **±365日** | 3日のみ | 別枠 |
| 空港の座標 | **含まれる** | 別APIが必要 | 無し |
| IANA TZ | **含まれる** | オフセットのみ | 無し |

triplot は空港を**場所（ピン）として登録**し、移動の `start_tz`/`end_tz` に **IANA
文字列**を入れる（`+09:00` では不可）。Amadeus だとこの2つが1回で揃わず、空港ごとに
別の検索を挟むことになる。過去 ±365日 も効く（旅行後に記録として入れられる）。

無料枠は 600 units/月で、この用途は **Tier 2 = 2 units/リクエスト**（実測）＝
月300照会。1旅行で数回の用途には桁違いに余裕がある。レート制限は 1 req/秒。

**乗り換えるときは `flightAeroDataBox.ts` だけを差し替える。** `flight.ts`（ドメイン）
と UI は提供元を知らない。

## 2. キーはサーバに置く

RapidAPI のキーは Google Maps のキーと違い、**利用元（bundle ID・リファラ）で
縛れない**。クライアントに置くと抜かれて枠を焼かれるので、Edge Function
（`supabase/functions/flight-lookup`）が預かる。

関数は**解析をしない薄い中継**。上流の応答をそのまま返し、変換も予測も呼び出し順の
判断も `packages/shared` に残す。Deno 側にロジックを置くと二重実装になり vitest の
テストが届かなくなる。

受け口はパスではなく**構造化した種別**（`flight` / `dates`）。パスを受け取って検証
する形は、書き漏らしがそのまま任意のエンドポイントへの踏み台になる。

`flight_api_cache` は RLS を有効にしてポリシーを1つも置いていない＝誰も直接読めず、
service_role で動く関数だけが触れる。メンバー全員が同じ便を開く経路と、編集のたびの
引き直しを潰す。TTL は便が30日・運航日一覧が90日
（当日のリアルタイム運航状況ではなく時刻表としての値だけが要るため長め。
無料枠300照会/月を節約する狙いもある）。

## 3. 解決の手順

```
① 対象日をそのまま照会
     ↓ 揃った答えが返ればそれが最良（source: actual）
② 返らない/片側が欠けたら、運航日一覧を引く
     ↓
③ 季節の近い運航日を選び、その日の実績から対象日を組み立てる（source: estimated）
```

呼び出しは最良1回・最悪3回。

**②で「直近の日」ではなく「時期の近い日」を選ぶ。** 対象が10月なら、直近の7月より
1年前の10月の方が当たる（`pickReferenceDate` は年をまたぐ通算日の距離で測る）。
過去 ±365日 が引けるという提供元の性質が、ここで**未来の予測精度**として効いてくる。

**IATA のダイヤ期間（夏/冬）で先に振り分ける細工は入れていない。** 一度実装しかけたが、
手元の実測がそれを支持しなかった: 同じ冬ダイヤの中で到着が 07:05 / 07:10 / 07:50 と
散り、夏（07:25〜07:50）と重なっていた。理屈としてダイヤ期間で組み替わるのは事実だが、
**この便に関しては説明力が無い**。出発時刻がどの時期でもほぼ不動である以上、どの日を
参照しても出発は当たり、到着は所要時間ぶんの誤差に収まる。実測が支持しない理屈で
分岐を増やさない。

**③で到着時刻はコピーせず、出発時刻＋所要時間から計算する。** 参照日と対象日で
サマータイムの有無が違うと、到着地の現地時刻をそのまま写したら1時間ずれる。所要時間
（絶対時刻の差）は時差もサマータイムも織り込み済みなので、これを足して到着地の TZ で
読み直す。`flight.test.ts` に冬→夏の実例を固定してある。

## 4. 提供元の癖（実応答をテストに焼いてある）

- **運航日でない日は 204**（空ボディ）。エラーではないので空配列として扱う
- **遠い日付では片側だけ欠けた応答が返る**。UA800 の +240日 は出発側が
  `{"name": "Boston"}` だけで、IATA も座標も時刻も無い（`quality` が空配列）。
  「便名を入れれば全部埋まる」前提で書くと壊れるので、欠けは `null` のまま持ち回り、
  UI が「手で入れてください」と出す
- 同じ便名が経由地で複数区間に分かれることがある（応答は配列）

作り物のフィクスチャだとこの癖が落ちるので、`flightAeroDataBox.test.ts` は**実際に
返ってきた JSON をそのまま**使っている。

## 5. 入力の導線

**タイトル欄の右端の飛行機アイコンで、その行がフライト入力に入れ替わる。** 専用の行を
足すとフォームが縦に伸びる（入力画面のスクロールを最小に保つ方針）。

1つの欄に何を打ってもよく、打った内容で分岐する（Flighty と同じ）。

- `ZG002` のような英数字 → 便名として直行
- `zipair` のような文字だけ → 航空会社の候補 → 選ぶと `[ZG]` がチップに畳まれ、
  数字だけの入力に進む

**モードを分けない**のが要点。「航空会社から探す」と「番号を打つ」を別 UI にすると、
どちらを使うか最初に選ぶ圧が生まれる。

**日付はフォームの日時をそのまま使う。** Flighty は単体アプリなので日付を聞くが、
予定フォームには既に日時欄があるので二度手間になる。

**結果は自動適用せず、必ずプレビューを1枚見せてタップで確定。** 便名の打ち間違いに
気付ける最後の場所であり、予測値かどうかもここで示す。

**空港名は日本語に差し替える。** 提供元は英語名しか返さない（"Tokyo Narita" /
"Honolulu"）。対訳表は Wikidata（CC0）から生成して同梱するが、350KB あるので
**動的 import** で初期バンドルから外し、フライトを引いたときだけ読む。読めなければ
英語名のまま動く（差し替えは表示上の改善で、機能の前提ではない）。

就航都市は **P931（place served by transport hub）** を使う。P131（行政区画）は
用途に合わない — 羽田が「大田区」、CDG が「ロワシー＝アン＝フランス」になる。
P931 なら「東京都」「パリ」で、タイトルに載せて自然な粒度になる。

航空会社リストは**静的に同梱**（`airlines.generated.ts`、Wikidata / CC0、943社）。
API に問い合わせないのは、航空会社を選ぶだけで有料枠を使うのが無駄で、1文字ごとに
候補を出すには往復が遅いから。オフラインでも航空会社は選べる。

同じ IATA コードを親会社と運航子会社が共有するので、**サイトリンク数＝知名度**が
最大のものを残す（`QF` は Eastern Australia Airlines ではなく Qantas Airways）。
生成物の並びも知名度順で、検索の同点処理を兼ねる。

## 6. 確定したときに埋まるもの

タイトル（`ZG002 東京 → ホノルル`）／移動 ON ／出発地・到着地／日時／タイムゾーン。

空港は**座標つきの自由入力**として登録する（`{"freetext": {name, lat, lng, icon}}`）。
Google 由来ではないので google 枝は使えず、かといって空港専用の変種を足すと次の
外部データ源でまた増える。座標は名前に付随する任意の属性として扱う
（[place spec](../../packages/shared/src/data/place.ts)）。座標があるので地図に
ピンが立ち、訪問順の並べ替え（`placeOrder`）でも座標つきとして扱われる。
