# 課金とプラン・利用枠の設計

有料プランと、それに紐づく利用枠（メール取り込みの月間上限）の設計。

> **実装状況**: 「利用枠の数え方」節だけが実装済み（メール取り込みの月間上限）。
> プラン・個別上書き・課金経路はまだ実装していない合意済みの設計。

## プランはユーザ単位・プラットフォーム非依存

**課金の権利はユーザに1つだけ持たせる。** iOS で買っても web で買っても同じ権利になり、
購入経路（App Store / web の決済）は権利の出どころを記録するだけで、権利そのものを
分けない。**「iOS で買った人は iOS だけ」のような経路ごとの権利分割はしない。**

## 利用枠の数え方: 残高ではなく計測

**利用枠は「上限値」であって、減っていく残高ではない。** 使用量は保存せず、
その月に処理済みのメールを都度数えて上限と比べる。

```
今月の使用量 = そのユーザの取り込みメールのうち、抽出時刻が月初以降のものの件数
判定         = 使用量 >= 実効上限 なら、抽出せず「枠超過」として保存だけする
```

**月初に枠を復活させる処理は存在しないし、作らない。** 月が変われば数える対象期間が
ずれるだけで、リセットすべきカウンタがどこにも無い。

残高方式（持ち点を保存して減算し、毎月補充する）を選ばない理由:

- 毎月動くバッチが必要になり、それが止まると全ユーザが枠を失う単一障害点になる
- 保存したカウンタと実データがずれうる（同じ事実を二重に持つ）
- 「補充が走る前に月初にアクセスしたユーザ」の扱いが要る

## 実効上限 = プランの上限と個別上書きの大きい方

上限を決める値を2つに分ける。**どちらが書き換わるかを完全に分離する**のが要点。

| 持つもの | 意味 | 書き換える主体 |
|---|---|---|
| プラン | 無料 / 有料など、現在の契約状態 | 課金・退会の処理だけ |
| 個別上書き（未設定可） | そのユーザ固有の優遇・個別対応 | 手動の運用操作だけ |

**実効上限 = max(プランの上限, 個別上書き)**（個別上書きが未設定なら 0 とみなす）

**`max` にする。** 単純に「個別上書きがあればそちらを優先」にすると、優遇されている
ユーザが課金した時にプランの上限より優遇値が優先され、**支払ったのに枠が増えない**。

期待する挙動（デフォルト30・優遇100・有料200 の例）:

| ユーザ | プランの上限 | 個別上書き | 実効上限 |
|---|---|---|---|
| 新規・無料 | 30 | なし | 30 |
| 優遇・無料 | 30 | 100 | 100 |
| 優遇・有料 | 200 | 100 | 200 |
| 優遇・退会後 | 30 | 100 | 100 |
| 新規・有料 | 200 | なし | 200 |

この形だと**課金処理はプランしか触らない**（退会も戻すだけ）。優遇は課金処理が一切
知らないので、契約状態が変わるたびに値を退避・復元するようなロジックが要らない。

## 既存ユーザの優遇はコードの分岐で表さない

将来デフォルトの上限を下げるとき、**その時点の上限を既存ユーザの個別上書きとして
一度書き込む**。以降コードに分岐は残らない。

**ユーザの作成日で分岐しない。** 分岐がコードに永久に残り、個別のユーザだけ調整する
ことができなくなる。「優遇フラグ」も作らない（2値しか表せず、3段階目が必要になった
時点で破綻する）。

## 機能の有効/無効（プランで機能を出し分ける場合）

課金で機能そのものを出し分けたくなった場合も、**呼び出し側は必ず「そのユーザの
実効的な権利を引く」1か所を通す**。プランに列を足すのか、プランと機能の対応表を
別に持つのかは、その内側の実装詳細として後から変えられるようにしておく。

**機能フラグ（段階的な公開・緊急停止・未完成コードの隠蔽）とは別の仕組みにする。**
両方とも結果は真偽値だが、寿命も持ち主も違う（機能フラグは公開しきったら消す一時的な
もの、権利は製品定義そのもの）。同じ仕組みで兼ねると、公開設定の変更で有料機能が
全員に開いてしまう事故が起きうる。**権利の判定は必ずサーバ側で行う。**
