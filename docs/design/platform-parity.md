# web と iOS で意図的に揃えていないもの

## 名前は両プラットフォームで揃える

同じものは**同じ関数を使う**（`packages/shared`）。プラットフォームの都合で共有
できない場合でも、**同じファイル名・同じ関数名・同じ i18n キー**にする。片方だけ
別名にすると、差分の総点検のたびにノイズになって本当の差分が埋もれる。

語彙が割れやすいところの決め: メール取り込み機能はアプリ側では **import**
（ファイル名・ルート・i18n の名前空間）。DB の実体は `inbound_emails` /
`inbound_drafts` なので、データ層の関数名だけ **inbound** を使う（`resolveInboundDraft`
等）。UI の文言は「取り込み」。


同じ機能は web（`apps/web`）と iOS（`apps/mobile`）で同じ形にするのが既定
（規約は [ui-guidelines.md](../ui-guidelines.md) の「web とネイティブ（RN）の
デザイン整合」）。ここはその**例外の一覧と、そう決めた理由**。

**ここに載っていない差分は「揃え忘れ」として扱ってよい。** 逆にここに載っている
ものは、総点検のたびに差分として拾い直して議論をやり直さないための記録。

| 何 | ある側 | 理由 |
|---|---|---|
| テーマ（Light/Dark/System）・言語の切替 | web | iOS は OS 設定に追従する（ui-guidelines の「プラットフォームの流儀を優先」） |
| 管理画面（`/admin`） | web | 運用者専用。モバイルで触る場面が無い |
| ランディングページ・プライバシーポリシー | web | iOS は「このアプリについて」から web の `/privacy` を開く。文面の単一の真実を保つ |
| 「このアプリについて」・オープンソースライセンス | iOS | App Store の要件由来。web は同じ情報をアカウントメニューのバージョン表示で足りている |
| `?` ヒント（`HelpTip`） | web | iOS は初回説明など別の流儀。当面は様子見とし、iOS でも説明が要ると分かった時は移植ではなく文言を短く自明にする方向で直す（ui-guidelines「文言は極力アイコンに寄せる」の順序） |
| 旅行のメンバー一覧（旅行詳細に常時表示） | web（広い画面のみ） | ヘッダーは web も iOS も2行タイトル（日程 ｜ 精算通貨）で同形。広い画面の web だけ余白があるので本文にメンバー一覧を置く。狭い画面と iOS では出さない（予定の色・費用のアバターで誰が関わるかは分かる） |
| 招待リンク再生成後の自動コピー | iOS | 下記 |
| 場所一覧のドラムロール操作 | iOS | 下記 |
| カテゴリ選択の中からのカテゴリ追加 | iOS | 下記 |

## カテゴリ選択の中からのカテゴリ追加

iOS は費用フォームのカテゴリ選択シートの末尾に「＋ カテゴリを追加」があり、その場で
作って選択まで終わる。web のカテゴリ選択にはこれが無く、費用カテゴリ管理（旅行の設定）
から追加する。改名・削除は**両方とも**費用カテゴリ管理にしかない
（理由は [ui-guidelines の「一覧の行から消せるようにするときの作法」](../ui-guidelines.md)）。

**揃えないのは、同じ不便さが web では起きないから。** カテゴリを足したくなるのは
「選ぼうとして当てはまるものが無い」瞬間だけで、そこから設定まで往復する重さが
プラットフォームで違う。iOS はシートを閉じて別のシートを開き直す（＝書きかけの
費用フォームを畳む）ことになるが、web は別タブ・戻るボタン・広い画面に旅行の設定を
並べて出せるので、往復が一手で済む。

**部品の事情も逆を向いている。** iOS のピッカーは自前のリストなので、行を1つ足すのに
制約が無い。web のカテゴリ選択は Base UI の Select で、「追加」は選択肢（値）ではない
ため素直には入らない。無理に入れると Select の意味論から外れた行を1つ抱えることになり、
得られる利得（往復が軽い web での短縮）に見合わない。

web 側でも往復が実際に煩わしいと分かったら、その時は Select ではなく Combobox
（場所入力と同じ step2 の部品）へ寄せる形で入れ直す。

## 招待リンク再生成後の自動コピー

iOS は共有リンクを再生成すると、新しいリンクをそのままクリップボードへコピーする
（再生成する人は次にコピーして配り直すので、2タップに分けさせない）。web は再生成
までで止め、続けて「リンクをコピー」を押してもらう。

**iOS の挙動の方が良いが、web が構造的に真似できない。** iOS Safari は非同期処理
（ネットワーク往復）を挟むと user activation が失効し、クリップボードへの書き込みを
拒否する。そのため web は「ポップアップを開いた時点でトークンを先に取得しておき、
コピーのタップ時は同期的に書き込む」形にしている。再生成はこの先読みができない
（開くたびに旧リンクを無効化してしまう）ので、新トークンはネットワーク往復後に
しか存在せず、コピーと分けるほかない。

## 場所一覧のドラムロール操作

一覧をスクロールすると選択中の場所が次々に切り替わり、地図のカメラと赤ピンが
追従する操作（iOS の場所タブ）。

**判定軸はプラットフォームではなく入力モダリティ。** 狭い画面の web はモバイルの
ブラウザ＝タッチなので、「web だからタッチ前提の操作は要らない」は成り立たない。
実際、週カレンダーの長押し→ゴーストやボトムシートはタッチ前提のまま web にも
実装している。

それでもこの操作を web に持ち込まないのは、**この操作の契約を成立させているのが
触覚だから**:

- iOS は行を1つまたぐごとにハプティクスを鳴らす（速いフリックでまたいだ時は
  その数だけ鳴らす）。「スクロールすると選択が変わる」という通常ではない挙動を
  ユーザーに納得させているのが、この触覚のフィードバック。
- iOS Safari には Vibration API が無い。モバイルウェブの利用者は iPhone が主なので、
  触覚のないまま地図だけが動く版になり、スクロールを乗っ取られたと読まれる。
- 価値のある半分（選択中の行が住所・◯日目・エリアを出して膨らむ）は web にも
  実装済み。残るのは1タップの節約で、実装面積（scroll-snap・交差監視・カメラ追従の
  自前実装）に見合わない。

再検討する時は、判定を幅ではなく `pointer: coarse` で行う。幅で判定すると、
デスクトップでウィンドウを細くしただけの利用者がホイールで選択を乗っ取られる。
Android が主戦場になれば Vibration API が使えるので前提が変わる。

## 全行が消せる一覧の削除: iOS はスワイプ / web はゴミ箱

対象は **TODO だけ**。行から直接消せる一覧は他にもあるが（メンバー・費用カテゴリ）、
そちらは**消せるのが一部の行だけ**なので両プラットフォームとも行のゴミ箱で揃っている
＝差分ではない。分かれるのは「全行が同じように消せる」一覧に限る
（費用・予定・場所は項目を開いてフォームの中で消すので、そもそもこの話に入らない）。

- **iOS**: 左スワイプで「削除」が出る。**常時表示のゴミ箱は置かない**
- **web**: 行にゴミ箱を常時表示

揃えない理由は入力モダリティではなく**操作の可視性**にある。マウスにスワイプは
無いので、web でスワイプ相当を作るなら hover で出すことになるが、それは「触れる
要素が、触れるまで見えない」形になる。逆に iOS で常時ゴミ箱を出すと、一覧の全行に
赤が並んで**赤が状態ではなく背景になる**（「要割当」を全行で琥珀にしていたのと
同じ失敗）。どちらのプラットフォームでも、その環境で自然な方を採っている。

**一部の行だけが消せる一覧でこれが逆転する**理由は
[ui-guidelines の「一覧の行から消せるようにするときの作法」](../ui-guidelines.md) にある
（赤が埋もれないうえ、ゴミ箱が「どの行が自分のものか」を示す手がかりを兼ねる）。

確認ダイアログを出すかどうかは、この分岐とは別に
[ui-guidelines の「確認の要否は復旧コストで決める」](../ui-guidelines.md) に従う
（TODO は安いので確認なし。ただしフルスワイプはアンドゥができるまで付けない）。
