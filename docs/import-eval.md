# 取り込みの評価

メール取り込みのモデルやプロンプトを変える前に、**実際のメールを流して、利用者が確定した
旅行と突き合わせて採点する**手順。モデルを替える・プロンプトを大きく直す時に、変える前と
変えた後を同じ物差しで比べる。

道具は `scripts/import-eval/`。取り込みそのものの設計は [design/import-flow.md](./design/import-flow.md)。

## 何と何を比べるか

- **流すもの**: Gmail のラベルにまとめた、ある旅行のメール一式（組。`test:seed-emails` の
  `--set` と同じ）。今あるのは `hawaii`（108通）。
- **正解**: その旅行を本番で利用者が取り込んで確定したもの（費用・予定）。利用者が手で直した
  値が入っているので、「画面でこう出てほしかった値」になっている。
- **比べる値**: **画面に出る値**。保存された下書きの値ではない。カードの通知の日時を現地に
  直す処理や、同じ時間・同じ場所の予定をまとめる処理は表示の時にかかるので、利用者が見る値は
  下書きと違う。

## 準備（初回だけ）

`apps/web/.env.local` に、組ごとの旅行の id を置く。本番の旅行の id を公開のリポジトリに
書かないためで、秘密の値ではない。

```
TRIPLOT_EVAL_STAGING_TRIP_HAWAII=<staging の評価用の旅行の id>
TRIPLOT_EVAL_PROD_TRIP_HAWAII=<正解にする本番の旅行の id>
```

staging の旅行は、開発用アカウントが入っている評価専用のものにする。流すたびに中身を
空にして作り直すので、他の確認に使っている旅行を指さない。

## 流し方

```bash
npm run eval:import:truth -- hawaii                         # 正解を本番から取り直す（本番の旅行を直した時）
npm run eval:import -- --set hawaii --name hawaii-flash-r3  # 1回流して採点する（1時間ほど）
npm run eval:import:compare -- hawaii-flash-r1 hawaii-flash-r3
```

`eval:import` がやること:

1. staging の評価用の旅行を**流す前の状態**にする — 中身を空にして、本番の旅行から時差の
   あるフライトだけを確定済みで写す。取り込みの日時はフライトの時差を前提に決まり、本番で
   利用者が取り込む時もフライトは先に確定しているため
2. 受信箱を空にして、組のメールを1通ずつ転送する（`test:seed-emails`）
3. 取り込みが全部終わるまで待つ。失敗して取り込み直しの予定が入ったものも、最後の試行まで
   待つ（最大6回・間隔を倍にしていくので1時間ほどかかることがある）。利用者が最終的に見るのは
   その結果のため
4. 結果を書き出し、画面に出る値に直して、正解と突き合わせる

途中で止まった時は、表示された開始時刻を `--since` に渡すと、待つところから続けられる。

- **結果はリポジトリの外**（`~/.triplot-eval/`）に置く。本物のレシートの中身と本番の
  旅行の中身を含むため。`<名前>.json`（取り込みの結果）・`derived-<名前>.json`（画面に
  出る値）・`score-<名前>.json`（採点）・`truth-<組>.json`（正解）。
- **本番は読むだけ。** 本番の問い合わせは書き込みのできない口から行う。staging は評価用の
  旅行の中と、開発用アカウントの受信箱だけを触る。
- **同じモデルでも回ごとに揺れる。** 比べる時は同じモデルを2回流し、揺れの幅を見てから
  差を判断する（2.5 Flash の2回で、予定の対応・出し過ぎ・取りこぼしが1〜2件動いた）。
- 1回の費用は、2.5 Flash で約 $2（108通）。

## モデルを替えて流す

取り込みのモデルはコードの既定値（`apps/web/lib/import/importConfig.ts`）で、環境変数
`IMPORT_LLM_MODEL` があればそちらを使う。比べたいモデルは staging にだけ置き、
終わったら消す。

```bash
npm run vercel -- env add IMPORT_LLM_MODEL --environment preview --git-branch staging \
  --value google/gemini-2.5-flash-lite --no-sensitive --yes --project triplot
# staging を出し直してから流す（環境変数は次のデプロイから効く）
npm run vercel -- env rm IMPORT_LLM_MODEL --environment preview --git-branch staging --project triplot --yes
```

採点の結果に、実際に呼ばれたモデルが出る（設定が効いているかはそこで確かめる）。

## 採点の規則

突き合わせは機械（`scripts/import-eval/score.mjs`）が行う。人が決めた扱いは次のとおりで、
回をまたいで変えない。

- **費用**は、同じ通貨・同じ金額で日付の近いものを相手にする。金額だけ違う（読み違い・
  利用者が直した）ものは、同じ日・同じ店・時刻が近ければ相手にする。
- **予定**は、画面でまとめた後の1件ずつで数える。相手は、同じメールの費用が対応した本番の
  費用の場所にある予定（カードの通知は店名が本番の場所の名前と似ないため）、無ければ場所・
  タイトルの似ている度合いと時刻の近さで決める。
- **数えないもの**は組ごとに `scripts/import-eval/sets.mjs` に書く。モデルに関係なく合体の
  規則で決まるもの（予約番号が同じ2人分の航空券が1件になる等）と、メールから来ていない
  本番の予定（手で入れたもの）。
- 同じ店で支払いが分かれて予定が2つ出たが、本番では1件にまとめてある時、余った方は
  **出し過ぎ**。厳しいが、モデルに関係なく一律に効くので比較はできる。
- 費用は取れていても、その出来事の予定の下書きが出ていなければ**取りこぼし**。

## これまでの結果

### 2026-10 のモデル比較（ハワイの組・108通）

正解は費用64件・予定57件（数えないものを除く）。費用・予定の「対応／出し過ぎ／取りこぼし」は
画面に出る値を正解と突き合わせた件数。項目の列は、対応したもののうち値が正解と一致した数。
同じモデルの回は平均せず、1回ずつ並べる。

| 回 | モデル | 費用（対応／出し過ぎ／取りこぼし） | 費用の項目（金額・日付・時刻・カテゴリ） | 予定（対応／出し過ぎ／取りこぼし） | 予定の項目（開始・終了） | 合体 | 108通の費用 |
|---|---|---|---|---|---|---|---|
| 1回目 | Gemini 2.5 Flash | 64／0／0 | 61・63・61・51 / 64 | 56／1／1 | 41・44 / 56 | 41 | $1.96 |
| 2回目 | Gemini 2.5 Flash | 64／0／0 | 60・63・61・49 / 64 | 56／8／1 | 34・39 / 56 | 41 | $1.79 |
| 1回目 | Gemini 2.5 Flash-Lite | 41／4／23 | 37・38・33・33 / 41 | 44／5／13 | 12・22 / 44 | 60 | $0.27 |
| 1回目 | Claude Haiku 5.5 | 57／7／7 | 54・45・39・44 / 57 | 52／5／5 | 30・31 / 52 | 37 | $0.37 |
| 1回目 | GPT-6 Luna | 61／3／3 | 59・59・55・50 / 61 | 53／7／4 | 32・33 / 53 | 40 | $0.19 |

- **Gemini 2.5 Flash の2回目**は、1回の合体で、候補に見せた他のメールの予定7件が写された
  （Issue #75。まれな不具合で、今は直していない）。写しが本番の予定の相手を先に取り、本物が
  出し過ぎに回ったので、予定の出し過ぎが8件になっている。写された7件を除いて採点し直すと
  予定は 57／1／0・開始 42・終了 46 / 57 で、1回目との差は1〜2件。同じモデルでも回ごとに
  この程度は揺れる。
- **Gemini 2.5 Flash-Lite** は別々の会計を合体してしまう（同じ店の別の会計・別の店・
  ホテルと夕食）。合体された側の費用は消えるので、費用の取りこぼしの大半はこれ。予定の時刻も
  大きく崩れた。
- **Claude Haiku 5.5**（考える量は初期設定のまま）は合体のしすぎは無いが、決まった形の誤りが
  4つあった。
  1. 銀行のカード通知の日付を現地の日付に直す印が付かず、1日先のまま（10件）。費用の日付・
     予定の時刻が合わない数の大半はこれ
  2. 銀行の仮の金額とチップ込みの確定額が合体されず、仮の金額のまま（4件。金額違いの
     出し過ぎと取りこぼしが1件ずつ出る）
  3. Square のレシート3通が、6回取り込み直しても答えの形（スキーマ）に合わず失敗
  4. ホテル（Expedia）と新幹線の費用の取りこぼし。予約のリマインダー1通を中身なしと判断
- **GPT-6 Luna**（考える量は初期設定のまま）は比べた中で一番安く、誤りは2つの形に偏っていた。
  1. 銀行の仮の金額とチップ込みの確定額が合体されず、仮の金額のまま（3件。費用の出し過ぎと
     取りこぼしはすべてこれ）。合体の判断を単独で2回呼んだ時も、2回とも「合体しない」と答えた
  2. Uber の乗車が崩れる。正解の乗車（移動）4件がすべて取りこぼしになり、代わりに普通の
     予定として作られたもの・時刻がずれたものが出し過ぎに回った。抜けたものもある。
     予定の出し過ぎと取りこぼしの大半はこれ
